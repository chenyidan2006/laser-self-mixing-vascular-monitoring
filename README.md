# 激光自混合干涉血管参数测量系统

一套基于激光自混合干涉（Laser Self-Mixing Interferometry，LSMI）的无袖带血管参数测量原型系统，覆盖激光微振信号采集、ESP32/STM32 传输、服务器算法、数据库和移动端 App。项目曾获第十四届全国大学生光电设计竞赛华北区一等奖，并获批全国大学生创新创业训练计划项目（尚未结题）。

本项目是在已有科研成果基础上的产品化与工程化实践。本人负责 App 前后端、ESP32 到服务器的通信，以及算法重训练、优化和部署联调。本仓库保留可公开的 App、硬件、通信协议和服务器算法快照；后端因部署与密钥管理需要独立维护。

## 理论来源与产品化关系

- Zhao 等人在 *Optics Express* 2024 论文中提出可穿戴自混合干涉传感器：激光照射桡动脉附近皮肤，动脉壁微弱形变改变外腔长度，反馈光进入激光腔形成自混合干涉信号；随后通过 CWT、相位处理/脉搏波重构和 CNN 估计 SBP、DBP。论文 DOI：[10.1364/OE.534566](https://doi.org/10.1364/OE.534566)。
- 后续研究采用 1310 nm DFB 激光器、ADS8688 与 STM32F407 形成小型化采集链路，并使用 RSAF 时频增强和 SA-CNN 直接从关键时频特征预测血压，减少完整相位解包裹和脉搏波重构步骤。
- 本仓库面向“从实验算法到可演示产品”的缺口，完成采集设备联网、二进制帧上传、服务器推理、数据库持久化、App 展示和部署文档。论文及毕业论文原文受版权和隐私约束，不随源码仓库分发。

## 数据链路

```text
双通道 LSMI 采集板 → ESP32-S3 → HTTP 原始帧接收 → MATLAB 编译算法 → 后端数据库 → App 展示
```

ESP32 每次上传一帧原始 SMI 数据；帧头将其声明为双通道、分块交错。当前 STM32 源码是否真的交替采集两个物理通道仍需实测确认。完整帧格式、采样点数和服务器拆帧逻辑见 [`prodict_algorithm_infuwuqi/FRAME_PROTOCOL.md`](prodict_algorithm_infuwuqi/FRAME_PROTOCOL.md)。

现役网络端口只有两个项目服务端口：ESP32 向 `3000` 端口上传原始帧；App 和算法向 `3002` 端口访问业务后端。MySQL 默认使用 `3306`，只供后端在服务器内部访问。算法由接收服务启动为本地子进程，本身不监听网络端口。

## 采样率、串口速率与 8 秒数据量

这几个数字属于不同层，不能都叫“采样率”：

| 参数 | 当前代码值 | 含义与代码依据 |
| --- | ---: | --- |
| ADC 触发频率 | `40,000 Hz` | STM32 TIM2：`84 MHz ÷ (83+1) ÷ (24+1) = 40,000 Hz` |
| STM32 → ESP32 UART | `1,152,000 baud` | STM32 `usart.c` 和 ESP32 固件两端一致，8N1、无流控 |
| SPI1 时钟 | 约 `5.25 MHz` | APB2 为 84 MHz，SPI1 预分频为 16 |
| 采集时间 | `8 s` | STM32 `SAMPLE_SECONDS` 与 ESP32 帧头 `secs=8` |
| 总 ADC 码数 | `320,000` | `40,000 × 8` |
| 二进制负载 | `640,000 bytes` | `320,000 × uint16 的 2 bytes` |

### 为什么程序设置为 40 kHz

现有聊天记录给出的设计思路是：先依据奈奎斯特采样定理，采样率应高于待测信号最高有效频率的 2 倍；考虑实际 SMI 信号质量、采集链路精度和滤波余量，工程上希望留到约 3–4 倍，讨论中先得到约 `20 kHz`，随后又把程序设为 `40 kHz` 以增加余量。

这段记录只能说明**当时选取 40 kHz 的工程理由**，不能据此断言老师的采集卡固定工作在 40 kHz，也不能反推出被测信号的最高频率。要复现老师采集卡的基准，还需要找到其型号、配置截图或原始数据的时间戳。仓库能够直接证实的是：当前 STM32 的 TIM2 确实产生 `40,000 Hz` 触发。

还要避免把两个“乘 2”混为一谈：

- 奈奎斯特的 `×2`：`采样率 > 2 × 信号最高频率`，是避免混叠的理论下限；实际系统通常还要为模拟滤波器过渡带和噪声留余量。
- 协议拆分的 `÷2`：服务器把总计 `40 kS/s` 的 160 个块按 `ch=2` 拆为两组，于是解释成每组 `20 kS/s`。这是数据格式的解释，不是奈奎斯特定理，也尚未证明对应两个物理 ADC 通道。

因此目前最严谨的表述是：“系统参考奈奎斯特准则并考虑低信噪比与采集误差，最终将 STM32 总触发率保守设置为 40 kHz；服务器按协议暂解释为两组各 20 kS/s。”不要写成“老师采集卡是 20 kHz，所以我们的双通道乘 2 得到 40 kHz”，因为现有材料不足以证明这条因果关系。

协议把 160 个块声明为双通道按块交替：

```text
2000 点/块 × 160 块 = 320000 点
160 块 ÷ 2 通道 = 80 块/通道
80 块 × 2000 点 = 160000 点/通道
160000 点 ÷ 8 秒 = 20000 点/秒/通道
```

因此服务器目前按“总计 40 kS/s、每通道 20 kS/s”解析，并从通道 1 取前 `100,000` 点，即 `100,000 ÷ 20,000 = 5 s`，输入旧模型。

但必须区分**协议声明**与**物理采样**：ESP32 只是给 640,000 字节补了 `ch=2` 头。当前 Keil 工程实际参与编译的 `ads8_test.c` 先发 `MAN_2`，之后连续发 `CONT`，源码没有展示两个物理 ADC 通道交替选择。因此现有代码能确认 40 kHz 触发和 8 秒总量，尚不能证明原始负载真的是两路各 20 kS/s。服务器现在的“通道 1/2”可能只是把同一连续数据流按 2,000 点块拆成两组；正式使用前应修改 STM32 通道切换逻辑并分别绘制两组波形验证。

### 1,152,000、2,000,000 和 4,000,000 到底是什么

仓库现役值是 `1,152,000 baud`，没有发现把 UART 配置成 `2,000,000` 或 `4,000,000` 的现役代码。如果后两个数字指 UART 波特率，它们只是候选传输速率，不是 ADC 采样率；如果指 SPI 时钟，也不能直接写成采样率。

UART 使用 8N1，每个数据字节在线路上约占 10 bit。只计算 640,000 字节负载时：

| UART 波特率 | 理论有效字节率 | 640,000 字节最短传输时间 | 4,000 字节块传输时间 |
| ---: | ---: | ---: | ---: |
| `1,152,000` | `115,200 B/s` | `5.56 s` | `34.72 ms` |
| `2,000,000` | `200,000 B/s` | `3.20 s` | `20.00 ms` |
| `4,000,000` | `400,000 B/s` | `1.60 s` | `10.00 ms` |

40 kHz 采样下每 2,000 点产生一个块，间隔为 `2,000 ÷ 40,000 = 50 ms`。当前 1,152,000 baud 发送一块约需 34.72 ms，理论上能在下一个块产生前发完；实际还要考虑 DMA 调度、中断、线缆质量和时钟误差。2 M/4 M 只能增加串口余量，不能改变 TIM2 的 40 kHz ADC 触发频率。

更完整的逐项计算与验证方法见 [`prodict_algorithm_infuwuqi/FRAME_PROTOCOL.md`](prodict_algorithm_infuwuqi/FRAME_PROTOCOL.md)。
