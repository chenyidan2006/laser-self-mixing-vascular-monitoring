# ADS8688 现役单通道帧、旧版布局与模型降采样

## 已确认结论

根据学长对实际系统的确认，并结合归档 STM32 代码：

- 现役 ADS8688 只采一个物理通道；
- STM32 定时采样率是 `40,000 Hz`；
- `1,152,000 baud` 是 STM32 → ESP32 的 UART 通信速率；
- 血压模型使用 `20,000 Hz` 数据训练；
- 采集端提高到 40 kHz 是为了获得更好的原始数据，不是因为同时采两个通道；
- 现役 40 kHz 连续单通道流应降采样到 20 kHz 后再进入模型；
- 早期确实写过双通道相关代码，但后来已经注释/停用；
- ESP32 帧头里的 `ch=2` 是遗留的硬编码兼容字段，不能再用来判断现役物理通道数。

归档 Keil 工程的构建记录也与此一致：参与链接的 `ads8_test.c` 每次 TIM2 中断只调用一次 `read_ch()`，第一次选择 `MAN_2`，之后连续发送 `CONT`；每次只追加一个 16 位采样，没有在两个 ADC 通道之间交替。

## 三个容易混淆的“2”

| 表述 | 真正含义 | 是否代表双通道 |
| --- | --- | --- |
| 帧头 `ch=2` | ESP32 中遗留的兼容字段，现役帧中与物理事实不一致 | 否 |
| 每点 `2 bytes` | ADS8688 采样保存为一个 16 位无符号整数 | 否 |
| `40 kHz → 20 kHz` | 为匹配模型训练采样率而做的 2 倍降采样 | 否 |

现役负载大小的正确计算是：

```text
40,000 点/秒 × 8 秒 = 320,000 点
320,000 点 × 2 字节/点 = 640,000 字节
```

这里没有乘通道数。单通道 40 kHz 和“总转换率 40 kHz 的旧双通道方案”都可能产生同样的 640,000-byte 负载，所以仅看文件长度无法判断布局。

## 二进制、16 位和十六进制不是一回事

每个 ADS8688 采样是一个 `uint16`，通过串口按两个二进制字节发送。帧头中的 `code=u16le` 表示：

```text
u16 = unsigned 16-bit integer
le  = little-endian，低字节在前
```

例如采样码 `0x1234` 在线路和 `.bin` 中占两个字节：

```text
34 12
```

“十六进制”通常只是人查看字节时使用的写法。原始 `.bin` 最节省空间；如果使用 `bin_convert_txt.m` 写成文本 `34 12 `，每个原始字节通常会变成两个十六进制字符加一个空格，文件反而约为原来的 3 倍。因此应表述为“以 16 位二进制保存，调试时可显示为十六进制”，而不是“十六进制更省内存”。

## 为什么帧头仍然写着 `ch=2`

ESP32 当前生成的历史兼容帧头是：

```text
#ADS8688 v1 rate=40000 secs=8 col=10000 blk=2000 nblk=160 ch=2 range=0x02 code=u16le\r\n
```

ESP32 不读取 ADS8688 寄存器，也不知道 STM32 实际选择了几个物理通道；它只是接收恰好 640,000 字节并拼接一行写死的文本。因此：

- `rate=40000` 与现役采样率一致；
- `blk=2000`、`nblk=160` 与传输分块一致；
- `code=u16le` 与实际 16 位小端字节一致；
- `ch=2` 是过时元数据，不能覆盖 STM32 单通道代码和学长确认的事实。

下一版协议应显式写成类似：

```text
ch=1 layout=continuous rate=40000 model_rate=20000
```

在 ESP32 固件和服务器解析器没有同步升级前，不能只改帧头中的一个数字，否则历史文件和新版文件会失去可区分性。更稳妥的是提升协议版本，并保留布局字段。

## 两种解析到底是什么

### 1. `continuous`：现役连续单通道

负载中的采样顺序是：

```text
s0, s1, s2, s3, ... s319999
```

所有点都来自同一个 ADS8688 通道，相邻点间隔为 `1 / 40000 s = 25 µs`。2,000 点只是 UART/DMA 发送块，不表示换通道：

```text
块0 = s0      ... s1999
块1 = s2000   ... s3999
块2 = s4000   ... s5999
...
```

为了送入按 20 kHz 训练的模型，应对整条连续流进行 2 倍降采样。正确的时间关系相当于均匀保留：

```text
s0, s2, s4, s6, ...
```

工程上应先使用与训练流程一致的抗混叠低通，再每隔一个点取一个点；不能用“隔一个 2,000 点块取一块”代替降采样。8 秒会得到约 160,000 点，模型再使用前 100,000 点，即 5 秒。

### 2. `interleaved`：旧版按块交替布局

本项目历史讨论中的 `interleaved` 指**按 2,000 点块交替**，不是常见的逐点 `A0,B0,A1,B1`：

```text
块0 = A0    ... A1999
块1 = B0    ... B1999
块2 = A2000 ... A3999
块3 = B2000 ... B3999
...
```

如果旧固件的总转换率为 40 kHz，那么 A、B 各得到名义 20 kS/s。解析通道 A 时取块 `0,2,4...`，解析通道 B 时取块 `1,3,5...`。这种方式只适用于确实由旧双通道固件产生的历史文件。

为了避免与逐点交错混淆，文档统一称它为 `block-interleaved`；命令行若继续保留旧名称 `interleaved`，也应在输出元数据中说明块长度。

## 为什么两种解析不能随便互换

假设现役连续单通道文件被错误当成旧版块交替：

```text
保留 s0...s1999
丢弃 s2000...s3999
保留 s4000...s5999
丢弃 s6000...s7999
...
```

得到的不是 20 kHz 均匀降采样，而是“保留 50 ms、丢掉 50 ms”的断续时间轴。每个保留块内部仍来自 40 kHz，块与块之间却缺失 50 ms，随后又被错误标成连续 20 kHz。这样会破坏周期、频谱、CWT 脊线、峰间距和心率特征。

反过来，如果真正的旧双通道块交替文件被当成连续单通道并逐点降采样，A/B 两个通道会每 50 ms 被拼在一起，也会产生台阶和伪频率。

因此，“输出刚好都是 160,000 点”不能说明解析正确。两种错误方式在点数上都可能看起来合理，但时间含义完全不同。

## `strong-lag-alternation` 是什么

你保存的旧讨论中出现过：

```json
"layout": "interleaved",
"auto_layout_rule": "strong-lag-alternation"
```

它表示一种**自动判断理由的名称**：程序观察多个 2,000 点块的均值、边界跳变或相关性，发现奇数块彼此相似、偶数块彼此相似，而相邻奇偶块差异持续存在，于是推测文件可能来自旧版 A/B 块交替布局。

它不是帧头字段，也不是物理双通道证明。单通道中的周期信号、直流漂移、块边界干扰也可能制造类似模式，所以这种规则只能作为旧文件恢复时的启发式判断，并应输出评分和人工对比结果。

更重要的是：当前代码中没有 `strong-lag-alternation` 的实现；已经删除的旧 `replay_old_frame_no_upload.py` 当时也没有 `--layout` 参数。你保存的命令属于曾经讨论过的目标设计，不能当成现有功能说明。

## 自动模式应采用的判断顺序

以后实现自动模式时，建议按以下证据优先级：

1. 新版帧头明确包含 `layout=continuous` 或 `layout=block-interleaved`；
2. 已知固件版本与文件时间能够确定布局；现役单通道固件固定判为 `continuous`；
3. 用户通过 `--layout continuous` 或 `--layout interleaved` 明确覆盖；
4. 只有来源不明的旧文件才运行 `strong-lag-alternation` 一类启发式检测；
5. 证据不强时不得默认为双通道，应报告“不确定”并输出两种解析的诊断对比。

对于当前硬件产生的新文件，正确结果应类似：

```json
{
  "layout": "continuous",
  "layout_source": "confirmed-current-single-channel-firmware",
  "source_rate_hz": 40000,
  "model_rate_hz": 20000,
  "physical_channels": 1
}
```

`strong-lag-alternation` 只可能用于来源不明的旧文件，不应覆盖已确认的现役固件事实。

## 2026-10-15 修复记录

修复前的 `project/frame_pipeline.py` 曾经：

1. 强制要求 `ch == 2`；
2. 把负载 reshape 成 2,000 点块；
3. 每隔一个块取通道 1；
4. 把结果标成 20 kHz。

这正是旧版 `block-interleaved` 解析，**不适用于已经确认的现役连续单通道固件**。已删除的旧回放脚本曾直接复用该函数，因此它过去也会得到同样的错误解释。

修复后读取全部连续采样，使用 `scipy.signal.resample_poly` 的Kaiser FIR低通先抗混叠，再按2倍均匀降采样；最终输出20 kHz前100,000点。ch=1/2均作历史元数据，显式非continuous布局会拒绝。支持 `--parse-only` 只解析而不写库。

仍需遵守：

- 不应把当前 Python 输出当成现役硬件的可靠模型结果；
- 不应把 fallback 演示值当作成功预测；
- 不应把错误拆块后的数据用于继续训练；
- 旧文件重放必须记录采用的布局，不能依赖过时的 `ch=2`。

当前解析已修复；合成回归验证的是时间轴和抗混叠性质。旧训练阶段具体滤波仍待核实，后续需用已知袖带真值做模型比较。比赛演示fallback按用户要求保留；安装、检查和回退命令见 [解析手册](../docs/PARSER_REPAIR_AND_ROLLBACK.md)。

## 数量和通信核算

| 项目 | 现役值 | 计算/说明 |
| --- | ---: | --- |
| 物理通道 | 1 | 学长确认，STM32 代码一致 |
| 原始采样率 | 40,000 Hz | TIM2：`84 MHz ÷ 84 ÷ 25` |
| 采集时长 | 8 s | 固件配置 |
| 原始采样点 | 320,000 | `40000 × 8` |
| 每点大小 | 2 bytes | `uint16` |
| 原始负载 | 640,000 bytes | `320000 × 2` |
| 模型训练采样率 | 20,000 Hz | 学长确认 |
| 8 秒降采样后点数 | 160,000 | `20000 × 8` |
| 模型实际输入 | 100,000 点 | 20 kHz 下前 5 秒 |
| UART | 1,152,000 baud | 8N1、无流控 |

UART 8N1 每字节在线路上约占 10 bit：

```text
整帧理论发送时间 = 640,000 × 10 ÷ 1,152,000 = 5.56 s
2,000 点块大小    = 2,000 × 2 = 4,000 bytes
块产生间隔        = 2,000 ÷ 40,000 = 50 ms
块理论发送时间    = 4,000 × 10 ÷ 1,152,000 = 34.72 ms
```

因此 UART 理论上能边采边发，但仍需实测 DMA、缓存和丢块情况。

## MATLAB 工具应怎样使用

[`tools/matlab/frame_fix_convert_plot.m`](../tools/matlab/frame_fix_convert_plot.m) 的 `blockSel=0` 会保留完整连续流，适合现役单通道文件的原始诊断；`blockSel=1/2` 是为旧版块交替文件和布局对比保留的诊断选项，不应再称为现役“两个通道”。

该 MATLAB 工具目前也没有实现“40 kHz 连续流 → 与训练流程一致的 20 kHz 模型输入”导出；它主要用于帧对齐、电压换算、频谱和滤波诊断。8 个图的解释见 [`tools/matlab/README.md`](../tools/matlab/README.md)。
