# Health Monitor App - 开发思路与问题解决记录

---

## 一、开发思路概述

### 1.1 整体架构设计

**核心目标**：构建一个可扩展、可维护的健康监测应用，支持多端运行（H5、微信小程序）。

**设计原则**：
- **微服务架构**：将认证和数据服务分离，便于独立扩展和维护
- **模块化设计**：前端页面按功能模块划分，后端按业务逻辑分层
- **模拟数据支持**：提供模拟数据接口，便于前端开发和测试
- **安全性考虑**：使用JWT进行用户认证，密码加密存储

### 1.2 架构演进历程

| 阶段 | 架构 | 问题 | 解决方案 |
|------|------|------|----------|
| v1 | 单体应用（app.js） | 所有功能耦合，维护困难 | 分离服务 |
| v2 | 双服务架构 | 端口冲突，配置混乱 | 统一API配置 |
| v3 | 前后端分离 | 跨域问题，部署复杂 | Nginx反向代理 |

## 二、核心问题与解决方案

### 2.1 问题一：验证码可见性问题

**问题描述**：用户反馈在登录时无法看到验证码发送位置，验证码输出混在大量日志中不易发现。

**根本原因**：验证码输出没有突出显示，与其他日志混在一起。

**解决方案**：
1. 在认证服务中增强验证码输出格式
2. 使用分隔线和emoji突出显示
3. 明确标注验证码有效期

**关键代码**（auth-server.js）：
```javascript
// 高亮显示验证码
console.log('');
console.log('========================================');
console.log(`📱 验证码已发送到手机: ${phone}`);
console.log(`🔑 验证码: ${code}`);
console.log(`⏱️  有效期: 5分钟`);
console.log('========================================');
console.log('');
```

---

### 2.2 问题二：服务分离需求

**问题描述**：用户要求将MySQL数据服务和验证码认证服务分开运行。

**根本原因**：单体应用架构导致服务耦合，不利于独立维护和扩展。

**解决方案**：
1. 创建 `auth-server.js`（端口3001）- 处理用户认证
2. 创建 `data-server.js`（端口3002）- 处理健康数据
3. 更新前端配置文件统一管理API地址

**架构变更对比**：

| 分离前 | 分离后 |
|--------|--------|
| 单端口3000 | 双端口3001/3002 |
| 所有API混在一起 | 按服务划分 |
| 单点故障 | 服务独立运行 |
| 难以扩展 | 可独立扩展 |

---

### 2.3 问题三：端口冲突

**问题描述**：启动服务时出现 `EADDRINUSE: address already in use` 错误。

**根本原因**：端口3000被其他进程占用。

**解决方案**：
1. 使用不同端口运行不同服务
2. 提供端口占用检测命令
3. 配置服务启动时自动检测并提示

**端口分配方案**：
| 服务 | 端口 | 用途 |
|------|------|------|
| 认证服务 | 3001 | 用户注册、登录、验证码 |
| 数据服务 | 3002 | 健康数据、设备管理 |

---

### 2.4 问题四：MySQL日期格式错误

**问题描述**：保存数据时出现 `Incorrect datetime value` 错误。

**根本原因**：JavaScript的ISO日期格式（如 `2026-05-07T10:53:02.329Z`）与MySQL的DATETIME格式不兼容。

**解决方案**：
1. 在保存数据前转换日期格式
2. 使用MySQL支持的格式 `YYYY-MM-DD HH:MM:SS`

**关键代码**（data-server.js）：
```javascript
// 转换日期格式
function formatDateTime(dateStr) {
  const date = new Date(dateStr);
  return date.toISOString().replace('T', ' ').substring(0, 19);
}
```

---

### 2.5 问题五：设备模拟器连接失败

**问题描述**：设备模拟器默认连接端口3000，但实际服务已迁移到端口3002。

**根本原因**：模拟器配置未更新，仍指向旧端口。

**解决方案**：
1. 支持通过命令行参数指定服务器地址
2. 更新使用手册说明新的连接方式

**使用方式**：
```bash
# 旧方式（已废弃）
node simulate_device.js

# 新方式
node simulate_device.js --server http://localhost:3002
```

### 2.6 问题六：趋势图表数据一致

**问题描述**：用户反馈心率、血压、血氧的趋势图数据完全一样。

**根本原因**：模拟数据生成逻辑存在缺陷，不同指标使用相同的随机数生成方式。

**解决方案**：
1. 为每个健康指标设计独立的随机数据生成逻辑
2. 根据各指标的正常范围生成合理数据

**数据范围配置**：
| 指标 | 正常范围 | 单位 |
|------|----------|------|
| 心率 | 60-100 | bpm |
| 收缩压 | 90-139 | mmHg |
| 舒张压 | 60-89 | mmHg |
| 血氧 | 95-100 | % |

---

### 2.7 问题七：算法调用失败

**问题描述**：调用预测算法 `callPredictFixed.exe` 失败。

**根本原因**：算法可执行文件可能不存在或权限不足。

**解决方案**：
1. 检测算法调用失败
2. 自动切换到模拟数据生成模式
3. 记录错误日志便于排查

**关键代码**（data-server.js）：
```javascript
try {
  const result = await executeAlgorithm(inputPath);
  return result;
} catch (error) {
  console.warn('算法调用失败,使用模拟数据:', error.message);
  return generateMockData();
}
```

---

### 2.8 问题八：前端API配置分散

**问题描述**：API地址硬编码在各个页面中，维护困难。

**根本原因**：缺乏统一的API配置管理。

**解决方案**：
1. 创建统一的API配置文件 `src/config/api.js`
2. 所有页面导入配置文件使用API地址
3. 支持灵活切换开发/生产环境

**配置文件结构**：
```javascript
const API_CONFIG = {
  auth: {
    baseUrl: 'http://localhost:3001',
    register: '/api/user/register',
    // ...
  },
  data: {
    baseUrl: 'http://localhost:3002',
    realtime: '/api/data/realtime',
    // ...
  }
};
```

## 三、技术决策记录

### 3.1 微服务拆分决策

**决策依据**：
- 认证服务和数据服务业务边界清晰
- 认证服务对响应速度要求高
- 数据服务可能需要更强大的数据库资源
- 便于独立部署和扩展

**拆分原则**：
- 高内聚：每个服务专注于单一业务领域
- 低耦合：服务间通过API接口交互
- 独立部署：服务可独立启动和停止

### 3.2 数据库选择决策

**选择MySQL的原因**：
- 稳定可靠，成熟的关系型数据库
- 良好的事务支持
- 社区活跃，文档丰富
- 适合存储结构化的健康数据

**数据模型设计**：
```
users (用户表)
  ├── id (主键)
  ├── phone (手机号)
  ├── password (加密密码)
  ├── nickname (昵称)
  └── created_at (创建时间)

health_data (健康数据表)
  ├── id (主键)
  ├── device_id (设备ID)
  ├── user_id (用户ID)
  ├── measure_time (测量时间)
  ├── heart_rate (心率)
  ├── systolic_bp (收缩压)
  ├── diastolic_bp (舒张压)
  ├── spo2 (血氧)
  └── algorithm_used (使用的算法)
```

### 3.3 认证方案决策

**选择JWT的原因**：
- 无状态认证，便于水平扩展
- 支持跨域认证
- 无需服务器端session管理
- 移动端友好

**认证流程**：
```
1. 用户登录 → 获取JWT Token
2. 前端存储Token → 每次请求携带Token
3. 后端验证Token → 返回数据
4. Token过期 → 重新登录
```

## 四、优化建议

### 4.1 性能优化

| 优化点 | 当前状态 | 建议改进 |
|--------|----------|----------|
| 数据库连接 | 单连接 | 连接池 |
| 数据缓存 | 无缓存 | Redis缓存 |
| 前端请求 | 频繁请求 | 请求合并/节流 |
| 图片资源 | 未优化 | 图片压缩/CDN |

### 4.2 安全性改进

| 安全项 | 当前状态 | 建议改进 |
|--------|----------|----------|
| 密码加密 | bcrypt | 增加加盐次数 |
| Token存储 | localStorage | HttpOnly Cookie |
| 接口限流 | 无限流 | 速率限制 |
| SQL注入 | 参数化查询 | 已实现 |

### 4.3 可维护性提升

| 方面 | 当前状态 | 建议改进 |
|------|----------|----------|
| 错误处理 | 基础处理 | 统一错误处理中间件 |
| 日志记录 | 控制台输出 | 结构化日志/ELK |
| 单元测试 | 无 | Jest/Mocha测试框架 |
| API文档 | 手动维护 | Swagger/OpenAPI |
